# Phase 7 — 버전을 이해하는 문서 검색과 채팅

## 사용법

1. 워크스페이스 왼쪽 **AI 채팅** 아이콘이나 오른쪽 **AI** 탭으로 채팅 패널을 펼친다. 패널 상단 접기 버튼으로 접어도 작성 중인 질문과 대화가 유지된다. 데스크톱에서는 캔버스와 채팅을 나란히 사용할 수 있다.
2. 왼쪽 메뉴 상단 버튼으로 메뉴를 접거나 펼친다. 접으면 문서·채팅 아이콘과 팀원 아바타가 남으며, 모바일은 기본적으로 압축 메뉴를 표시한다.
3. 상단의 문서 검색 준비 상태를 확인한다. 새 READY 문서는 자동으로 색인된다.
4. 질문을 보내면 답변이 비동기로 표시된다. `S1` 같은 인용 버튼을 누르면 문서 이름, 버전, 페이지/문단과 발췌문을 볼 수 있다.
5. **인용한 버전 열기**는 답변이 참조한 버전과 문단을 연다. 현재 버전이 이후 변경되어도 저장된 출처는 바뀌지 않는다.
6. **대화 기록**은 같은 워크스페이스 구성원에게 공유된다. 새 대화, 기록 복원, 마지막 실패 답변 재시도를 지원한다.
7. **문서 검색** 탭에서는 답변을 생성하지 않고 검색된 본문을 바로 확인한다.

OWNER/EDITOR/VIEWER 모두 검색과 질문을 할 수 있다. 색인 재시도는 OWNER/EDITOR만 가능하다. 워크스페이스가 다른 세션이나 문서는 검색할 수 없다.

## 버전 범위

| 선택 | 동작 |
|---|---|
| 질문에 맞게 | 기본은 현재 버전. ‘과거’, ‘지난’, ‘작년’, ‘이전 버전’, 연도 표기 등의 표현이 있으면 과거 버전도 포함한다. |
| 현재 버전 | 각 문서에서 사용자가 지정한 current_version_id만 검색한다. |
| 과거 버전 포함 | 워크스페이스의 모든 READY 버전을 검색한다. |
| 기준일 당시 | 한국 시간 해당 날짜 말까지 생성·업로드된 READY 버전 중 문서별 가장 높은 버전 번호를 검색한다. |

‘기준일 당시’는 해당 날짜의 **현재 버전 지정 이력**을 복원하는 기능이 아니다. 현재 버전 변경 이력은 별도로 저장하지 않는다. 자동 범위 판별은 규칙 기반이며 사용자가 범위를 직접 지정할 수 있다. 버전 전환은 검색 범위에 즉시 반영된다.

## 처리 구조

- 정규화된 S3 문서 전체를 최대 1,600자 구간으로 나눈다. 긴 문단은 160자가 겹치며, 각 구간은 정확한 블록 ID·문단 내부 문자 범위·페이지 등 원본 위치를 보존한다. 문서당 최대 2,500구간을 넘으면 색인이 실패한다.
- `rag_indexes`의 DB outbox와 Celery 작업이 한 번에 16구간씩 임베딩한다. 완료한 구간은 재사용하고, 작업 중단·중복 전달은 lease token으로 처리한다. 최대 3회 실패하면 명시적 재시도를 기다린다.
- `document_chunks`의 네이티브 pgvector 컬럼에서 cosine distance를 계산한다. SQL에 workspace와 버전 범위를 먼저 제한한다. 같은 임베딩 설정과 차원의 벡터만 비교한다.
- 의미 검색 후보와 정확한 문자열 검색 후보를 순위로 합친다. 최대 8개 구간, 버전당 최대 3개를 답변 근거로 제공한다. 짧은 후속 질문은 같은 세션의 이전 질문을 검색 맥락에 더한다.
- `AIService`를 통해 근거·질문·최근 대화만 전송한다. 모델의 각 답변 항목은 검색된 출처 ID를 인용해야 한다. 알 수 없는 ID, 잘못된 JSON은 게시하지 않는다. 근거가 없으면 추측 대신 근거 부족을 표시한다.
- `chat_sessions`, `chat_messages`에 요청 UUID와 순서를 저장한다. 응답 유실 후 재전송은 중복 질문을 만들지 않는다. 같은 세션의 답변은 한 번에 하나이며 세션당 50회 질문까지 허용한다.
- 답변과 출처는 일반 텍스트로 렌더링한다. HTML·스크립트·문서 안의 명령을 실행하지 않는다.

인용 검증은 **검색된 출처의 실제 존재와 연결**을 보장한다. 모델이 원문을 완벽하게 해석했는지까지 증명하지 않으므로 답변과 함께 원문을 확인할 수 있도록 제공한다. 긴 문서 전체의 완전한 요약이나 모든 변경점의 나열을 보장하지 않는다.

## 실행과 설정

기존 Phase 6 AI 환경 변수를 그대로 사용한다. API 키는 백엔드·worker에서만 읽는다. `MINDLOGIC_API_KEY`, `MINDLOGIC_BASE_URL`, `AI_MODEL`, `AI_EMBEDDING_MODEL`을 변경하면 해당 서비스들을 다시 생성한다.

```bash
docker compose --env-file .env.development up -d --build
```

PostgreSQL 17 Alpine에 pgvector 0.8.7을 빌드한 이미지를 사용한다. 기존 `postgres_data` 볼륨을 그대로 사용하며 `0008_workspace_rag` migration이 확장과 테이블을 생성한다. Docker 없이 실행하는 DB도 먼저 pgvector를 설치해야 한다. 확장 생성 권한이 필요하다. 기존 데이터가 있는 환경은 적용 전에 DB 백업을 만든다.

현재 구현은 정확한 벡터 거리 검색이며 ANN 인덱스를 두지 않는다. 검색 결과 누락 없이 시작하기 위한 선택으로, 대규모 corpus에서는 차원 고정·HNSW 인덱스·검색 품질/성능 평가를 별도로 진행해야 한다. [pgvector 공식 문서](https://github.com/pgvector/pgvector)를 참고한다.

임베딩 모델·endpoint·chunk 알고리즘을 변경하면 dispatcher가 기존 색인을 무효화하고 다시 생성한다. `AI 채팅 → 색인 다시 시도`로 실패한 색인을 재개한다. 403은 AI 접근 권한 오류로 표시하며 자동으로 무한 재시도하지 않는다. 의미 검색을 사용할 수 없으면 텍스트 검색으로 전환하고 화면에 알린다. 색인 미완료 문서가 있으면 별도로 안내한다. 아직 본문 구간이 생성되지 않은 문서는 텍스트 검색에서도 제외된다.

## API

모든 경로의 prefix는 `/api/workspaces/{workspace_id}`다. 인증과 membership을 확인하며 응답은 `Cache-Control: no-store`다.

| Method | 경로 | 기능 |
|---|---|---|
| GET | `/rag/status` | 현재/전체 버전 색인 상태 |
| POST | `/rag/reindex` | 누락 색인 등록·실패 색인 재시도 |
| POST | `/search` | `{question, scope, as_of}` 검색 |
| GET / POST | `/chat/sessions` | 공유 대화 목록 / 생성 |
| GET / POST | `/chat/sessions/{session_id}/messages` | 기록 / 질문 전송 |
| POST | `/chat/sessions/{session_id}/messages/{message_id}/retry` | 마지막 실패 답변 재시도 |

세션 생성과 질문 전송에는 UUID `request_id`가 필요하다. scope는 `auto`, `current`, `history`, `as_of` 중 하나다. `as_of`는 기준일 범위에서만 `YYYY-MM-DD`를 받는다. 목록은 50개씩 `offset`으로 조회하며 한 세션의 메시지는 최대 100개다.
