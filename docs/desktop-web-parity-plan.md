# ConText 웹·데스크톱 공통 환경 실행 계획

작성일: 2026-10-25 (한국 시간)

상태: 계획에 따른 로컬 구현과 macOS 패키징 검증 완료. 실제 OAuth·개인 실계정·Windows 검증과 후속 동기화는 별도 범위다. 단계별 상태와 실제 검증 결과는 `desktop-web-parity-progress.md`, `desktop-web-parity-verification.md`에 기록한다.

## 1. 목표와 결정 사항

웹과 데스크톱에서 같은 화면, 문서 모델, 편집 방식, 문서 맥락 관리 기능을 제공한다. 데스크톱은 사용자가 연결한 로컬 폴더를 중심으로 동작하며, 기본 문서 작업은 로그인·Docker·인터넷 없이 사용할 수 있어야 한다. 이후 선택적 웹 동기화를 붙일 수 있게 문서 식별자와 변경 기록을 준비한다.

- 공통화 대상: 작업 화면, 캔버스, 문서 읽기, 편집기, 관계·메모·버전, 검색, AI 채팅·작성·출처, 내보내기 흐름.
- 웹 구현: Next.js 진입점·인증, 서버 API, PostgreSQL, S3, 팀 권한.
- 데스크톱 구현: Electron 진입점, 제한된 IPC, 로컬 파일, SQLite, 로컬 처리 프로세스, OS 연동.
- AI 연결: 서버가 제공하는 기본 ChatKHU와 사용자가 등록한 개인 ChatKHU API 키를 지원한다.
- AI 자료 준비와 결과 저장은 해당 작업 공간의 저장 위치를 따른다. 로컬 자료로 AI를 사용하기 위해 웹에 작업 공간을 먼저 생성하거나 원본 파일을 업로드하도록 요구하지 않는다.
- 웹의 팀 초대·권한과 데스크톱의 폴더 연결·Finder/탐색기 열기는 환경별 기능이다. 공통 기능의 배치와 조작은 일치시키고 사용 불가 기능은 이유를 표시한다.
- 양방향 동기화, 실시간 공동 편집, 서명·공증·자동 업데이트의 운영 배포는 후속 단계로 둔다. 이를 제외한 기능 이식은 전체 목표에 포함하며 미완료 항목을 별도로 추적한다.

이번 실행의 추론 설정은 사용자가 선택한 Extra High를 따른다. 개발 도구의 모델·추론 설정은 앱 내부 ChatKHU 모델 선택과 독립적이다. ChatKHU 모델은 연결 계정에서 실제 조회한 목록으로 선택한다.

## 3. 공통 구조

권장 모듈 경계는 다음과 같다. 실제 이동은 기능 단위로 수행하며 처음부터 전체 저장소나 패키지 관리 방식을 교체하지 않는다.

| 모듈 | 책임 | 허용하지 않는 의존성 |
|---|---|---|
| `packages/core` | 문서·버전·출처·편집 스키마, 저장 충돌·작업 상태, 어댑터 계약 | Next.js, Supabase, Electron, 파일 시스템 |
| `packages/ui` | 공통 작업 화면과 기능별 React 컴포넌트·스타일 | 서버 주소, API 키, Node API, 직접적인 HTTP/IPC 호출 |
| 웹 어댑터 | 공통 계약을 기존 HTTP API·인증·브라우저 다운로드에 연결 | 데스크톱의 로컬 경로 가정 |
| 데스크톱 어댑터 | 공통 계약을 preload API·파일 대화상자·로컬 저장에 연결 | 렌더러의 직접 파일·비밀 키 접근 |
| Python 공통 처리 모듈 | 정규화·비교·출력의 결정적 처리 | 웹 사용자 세션·S3·DB 세션 |

실제 공통 모듈은 기존 프런트 빌드 경계를 유지하도록 `frontend/shared/{core,ui,writing,chat,canvas}`에 구현했다. 아래 계약 이름은 설계의 책임 구분이며 실제 기능에 필요한 인터페이스부터 추출했다.

필수 계약은 `WorkspaceRepository`, `DocumentRepository`, `CanvasRepository`, `DraftRepository`, `SearchService`, `AIConnectionService`, `AIService`, `ExportService`, `HostActions`로 시작한다. 목적 없는 범용 프레임워크를 만들지 않고 첫 수직 기능에 필요한 메서드부터 추가한다.

- 문서 저장은 `expectedRevision`을 받아 오래된 편집의 덮어쓰기를 거부한다.
- 변경 이벤트, 작업 진행률, 취소, 오류 코드와 재시도 가능 여부를 공통으로 표현한다.
- `capabilities`로 읽기·편집·버전 복원·형식별 출력·온라인 AI 가능 여부를 전달한다. 권한의 최종 검사는 서버 또는 Electron 경계에서 수행한다.
- 화면의 주 메뉴, 패널 위치, 선택·검색·편집·비교 방식, 접근성 이름을 공통으로 유지한다. 저장 위치는 웹의 클라우드 작업 공간과 데스크톱의 연결 폴더로 명확히 표시한다.
- 공통 패키지의 React는 중복 번들되지 않게 의존성을 정리한다. Next.js와 Vite 양쪽 빌드를 매 추출 단계에서 확인한다.
- `frontend/AGENTS.md`에 따라 프런트엔드 구현 전 설치된 Next.js의 서버·클라이언트 경계 및 관련 패키지 가이드를 읽는다.

## 4. 로컬 데이터와 파일의 규칙

### 4.1 원본과 편집 데이터

- 연결한 폴더의 파일은 원본 위치에 둔다. 폴더 연결은 전체 파일 복사나 클라우드 업로드를 발생시키지 않는다.
- 앱 DB에는 문서 식별자·배치·관계·메모·초안·작업 상태를 저장한다. 본문 색인·필요한 버전 스냅샷은 앱 데이터 영역에 보관한다.
- 앱에서 작성한 문서는 공통 블록 스키마로 저장하고 DOCX/HWPX 등으로 내보낸다. 내부 초안 저장과 사용자 폴더로 파일 저장을 UI에서 구분한다.
- 외부 DOCX/HWPX/PDF를 정규화한 뒤 원본 서식을 그대로 보존해 편집하는 기능으로 표시하지 않는다. 추출 내용을 편집할 때는 새 초안으로 만들고 원본과 연결한다.
- TXT/Markdown 직접 편집은 지원 범위와 인코딩 보존 여부를 명시한다. 지원하지 않는 변환을 무손실 저장으로 표시하지 않는다.
- 캔버스 위치·논리적 그룹 변경은 디스크 이동을 일으키지 않는다. 실제 파일 이동·이름 변경·삭제는 별도 명령으로 제공하고, 삭제는 지원 OS의 휴지통 경로를 우선 사용한다.

### 4.2 식별자·버전·검색

- 기존 로컬 workspace/entry UUID와 배치를 보존한다. 파일 항목과 논리 문서를 연결하되 경로나 inode를 동기화용 문서 ID로 쓰지 않는다.
- 문서 ID, 불변 버전 ID, 현재 편집 revision, 기기별 상대 경로, 콘텐츠 해시를 분리한다.
- 외부 편집 프로그램의 교체 저장·이름 변경을 기존 엔진의 식별 규칙과 함께 검증한다. 해시가 같다는 이유만으로 별개 문서를 자동 병합하지 않는다.
- 과거 원본이 저장되지 않았으면 복원을 제공하지 않는다. 최초 색인 이전의 이력을 추측해서 생성하지 않는다.
- 검색은 파싱한 본문과 출처 위치를 저장한 뒤 SQLite FTS5를 우선 검토한다. 실제 Electron SQLite의 FTS5 지원과 한글 부분 검색을 확인하고 토크나이저·텍스트 보완 검색을 결정한다.
- 임베딩은 선택적 향상 기능이다. 연결·모델·차원·색인 알고리즘의 fingerprint로 구분하고 변경 시 무효화·재색인한다. 다른 계정·모델의 벡터를 섞지 않는다.
- 파일 변경 후 해당 문서의 현재 버전만 증분 갱신한다. 이전 인용은 기존 버전 스냅샷에 남기고, 원본이 사라졌을 때도 출처 상태를 설명한다.

### 4.3 안전한 저장과 복구

- SQLite `user_version`을 무조건 1로 설정하는 현재 초기화 방식을 순차 마이그레이션으로 바꾼다. 기존 사용자 DB와 신규 DB를 모두 검사한다.
- 마이그레이션 전에 SQLite backup API 또는 일관성이 보장된 체크포인트·닫기 절차로 백업한다. 실행 중 WAL을 제외한 DB 파일 하나만 복사하지 않는다.
- 앱 metadata 변경과 전송 대기용 변경 기록은 같은 DB 트랜잭션으로 저장한다.
- 파일 시스템과 SQLite는 하나의 트랜잭션이 아니므로 저장 journal, 임시 파일, 교체 단계와 재시작 복구 규칙을 둔다.
- 원본의 기준 해시·수정 상태를 저장 직전에 확인한다. 외부 변경 또는 동시 편집이 감지되면 원본과 편집안을 모두 보존하고 사용자가 선택하게 한다. 외부 앱과의 경쟁 조건도 실제 파일로 검증한다.
- 읽기 권한 상실·외장 드라이브 해제·부분 스캔·파싱 실패를 파일 삭제로 오인하지 않는다.
- 폴더 연결 해제는 원본 파일을 삭제하지 않는다. 스냅샷·초안 등 앱 내부 자료의 보존/정리 정책은 사전에 화면에 표시하고 확인한다.

## 5. ChatKHU 연결 설계

### 5.1 두 연결 방식

| 환경 | 기본 ChatKHU | 내 ChatKHU |
|---|---|---|
| 웹 | 인증된 ConText 서버가 서비스용 키로 호출 | 서버가 요청자 소유의 암호화된 개인 키로 중계 |
| 데스크톱 | ConText 계정 연결 후 서버 중계 | Electron main 또는 제한된 처리 프로세스가 개인 키로 직접 호출 |

개인 ChatKHU는 API Gateway 키 등록 방식으로 시작한다. ChatKHU 웹 비밀번호·쿠키를 받거나 자동 로그인으로 연결하지 않는다. 개인 키 호출의 크레딧은 해당 키의 소유 계정에서 차감된다.

기본 연결은 운영자가 서비스 용도로 사용할 수 있는 자격 증명과 이용 대상·사용량 정책을 정해야 한다. 앱에 공용 키를 배포하지 않으며, 데스크톱 기본 AI를 위한 계정 로그인은 로컬 문서 이용과 분리한다. 기존 Google/Supabase 인증을 데스크톱에 연결할 때는 시스템 브라우저와 PKCE를 사용하고 callback·세션 저장을 검증한다.

### 5.2 데이터 경로

- 로컬 검색·근거 수집은 데스크톱에서 수행한다. 모델에 전달할 요청에는 필요한 발췌문·정확한 문서/버전/문단 참조·현재 초안만 포함한다.
- 기존 웹 RAG·작성 API는 서버 DB의 작업 공간을 조회한다. 따라서 로컬 문맥을 전달받는 인증된 AI 요청 계약을 별도로 추가해야 한다.
- 이 서버 경로는 입력 크기·작업 종류·모델·사용량을 제한하고 원문·키를 로그에 남기지 않는다. 기본 정책으로 원본·초안·대화를 서버 문서 저장소에 영구 저장하지 않는다. 최소 요청 상태·사용량 metadata의 보관은 별도 정책으로 둔다.
- 모델이 반환한 출처 ID를 전달한 근거 목록과 대조한다. 문서 내용은 지시가 아닌 자료로 처리하고, AI 수정은 제안으로 저장한 뒤 사용자가 적용한다.
- 로컬 출처 ID를 서버 문서 ID처럼 조회하지 않는다. 서버에서 외부 경로나 URL을 읽어 달라는 입력은 받지 않는다.
- AI 호출이 가능해도 파일 동기화가 활성화된 것으로 간주하지 않는다. AI에 전송되는 자료 범위는 설정과 요청 화면에서 알 수 있게 한다.

### 5.3 자격 증명·모델·실패 처리

- Electron 개인 키는 검증된 OS 보안 저장 방식으로 보관한다. 지원 OS의 암호화 상태를 확인하고 평문 저장으로 자동 전환하지 않는다. 키 전체를 preload 응답·SQLite·웹 저장소·로그로 내보내지 않는다.
- 웹 개인 키는 서버 외부에서 관리하는 암호화 키로 암호화하고 사용자 소유권을 강제한다. 요청·worker 실행 때 실제 요청자의 연결을 사용하며 팀 소유자 키를 자동 차용하지 않는다.
- 웹과 데스크톱의 연결 설정 UI는 이름·연결 방식·선택 모델·연결 상태·키 교체/삭제 동작을 공유한다. 키 자체는 문서나 향후 작업 공간 동기화에 포함하지 않는다.
- 모델 목록은 연결한 자격 증명의 `/models/`로 조회한다. 기존 기본값 `gpt-5.6-luna`는 접근 가능 여부를 확인해 사용하고, 목록에 없으면 선택을 요청한다. 하드코딩된 최신 모델 목록으로 대체하지 않는다.
- 모델별 JSON 응답·추론 옵션·토큰 제한·취소·스트리밍 지원을 확인한다. 지원하지 않는 옵션을 무조건 전송하지 않는다. 스트리밍이 없어도 같은 작업 상태 UI로 동작해야 한다.
- 생성과 임베딩 연결·모델을 구분한다. 임베딩이 없는 계정도 로컬 텍스트 검색으로 근거를 모아 생성할 수 있어야 한다.
- 오류는 인증 실패·크레딧/사용량 제한·시간 초과·네트워크·지원하지 않는 모델/옵션·출처/응답 검증 실패로 구분한다.
- 개인 연결 실패 시 기본 연결로 자동 전환하지 않는다. 연결 또는 유료 모델 전환은 명시적 선택으로 처리한다.
- request ID로 동시 중복 요청을 억제하고 결과를 재사용한다. 상위 서비스의 처리 여부가 불명확한 요청은 무조건 재전송하지 않는다. 외부 API의 정확히 한 번 과금은 보장한다고 표시하지 않는다.

## 7. 실행 순서와 단계별 완료 조건

작업 시간보다 의존성과 검증 통과를 기준으로 진행한다. 각 단계의 실패는 해당 경계를 고친 뒤 다음 단계로 넘어간다. 여러 단계를 한 번에 옮기고 마지막에 빌드하는 방식은 피한다.

### P0 — 기준선과 기능 목록 확정

1. 저장소 지침·기존 변경·실행 가능한 도구를 확인한다. 비밀 값을 출력하지 않고 관련 설정의 존재 여부만 확인한다.
2. 현재 화면과 지원 기능을 기록하고 공통/환경별 기능의 체크리스트를 만든다.
3. 웹 타입·린트·빌드, 데스크톱 빌드·엔진 테스트를 실행해 기존 실패와 새 실패를 구분한다.
4. 파서 프로세스를 패키징된 앱에서도 실행할 수 있는지 작은 검증을 수행한다. Python runtime·라이브러리를 포함하는 방식을 우선 검토하며 Docker·시스템 Python을 최종 사용자의 필수 조건으로 만들지 않는다.

완료 조건: 기준선 보고서와 파일 보존 목록, 파서 실행·배포 방식, 검증 명령이 기록되어 있다.

### P1 — 공통 계약과 첫 화면 추출

1. 공통 문서·출처·revision·작업 상태와 첫 어댑터 계약을 정의한다.
2. 기존 카드·토큰을 재사용하면서 공통 작업 프레임·선택·미리보기 패널부터 추출한다.
3. 웹은 기존 API를 감싼 어댑터, 데스크톱은 기존 IPC를 감싼 어댑터로 연결한다.
4. 기존 로컬 폴더 탐색·이름 검색·감시·배치 복원과 웹 로그인·권한을 유지한다.

완료 조건: 공통 컴포넌트가 양쪽 빌드에 실제 사용되고 기존 작업 공간이 그대로 열린다. 스타일만 비슷한 별도 구현으로 완료 처리하지 않는다.

### P2 — 로컬 저장과 편집의 수직 기능

1. 기존 DB의 순차 마이그레이션과 초안·revision·변경 기록·저장 journal을 구현한다.
2. 공통 Editor.js 편집기로 새 초안을 만들고 제목·본문·목록·표를 저장한다.
3. 로컬 읽기와 초기 TXT/MD 저장·다른 이름 저장을 연결한다. 지원 범위 밖 원본은 새 초안으로 처리한다.
4. 강제 종료·재실행 복원, 외부 수정 충돌, 저장 실패 복구를 검사한다.

완료 조건: 인터넷과 로그인이 없는 상태에서 폴더 연결 → 문서 열기 → 초안 편집 → 로컬 저장 → 앱 재실행 → 복원까지 동작한다.

### P3 — 파싱·본문 검색·출력

1. 검증한 로컬 처리 프로세스로 PDF/DOCX/HWPX 파싱을 연결한다. 작업 제한·취소·프로세스 종료·재시도를 둔다.
2. 정규화 본문·버전·위치 정보를 저장하고 현재 문서의 한글 본문 검색을 구현한다.
3. 외부 파일 변경에 대한 재파싱·색인 무효화·증분 갱신을 연결한다.
4. 기존 변환·작성 출력 코드를 재사용해 DOCX/HWPX 및 PDF/TXT/MD 내보내기를 연결한다. PDF 폰트와 한글 출력을 실제 산출물로 확인한다.
5. 패키징된 앱에 필요한 runtime·라이브러리·출력 자산을 포함한다.

완료 조건: 시스템 Python·Docker가 없는 배포 형태에서 로컬 본문 읽기·검색·출력이 가능하고 오류·제한을 화면에서 확인할 수 있다. 개발 환경 실행만 통과하면 패키징 검증은 미완료로 남긴다.

### P4 — ChatKHU 두 연결 방식

1. 요청자별 연결·모델·작업 종류를 전달하는 공통 AI 계약을 구현한다.
2. 데스크톱 개인 키 보관·연결 검사·모델 조회·삭제와 직접 호출을 구현한다.
3. 기본 연결용 데스크톱 계정 인증과 로컬 근거를 받는 서버 중계 경로를 구현한다.
4. 웹의 개인 키 등록·암호화 보관·소유권 확인·모델 선택을 구현한다. 운영 암호화 설정이 없으면 등록을 비활성화하고 필요한 설정을 안내한다.
5. 공통 채팅·요약·작성에 연결하고 제안 적용·출처 이동·로컬 결과 저장을 검사한다.
6. API 응답 대역으로 오류·모델 차이·중복 요청을 검증한다. 실제 호출은 설정된 사용 가능 계정에서 합성 자료로 소량 수행하고 연결 방식별 결과를 구분한다.

완료 조건: 두 연결 경로가 구현되고, 실제 연동을 검증한 범위와 설정 부족으로 확인하지 못한 범위가 구분된다. 버튼만 있거나 대역 응답만 통과한 상태를 실제 ChatKHU 연동 완료로 표시하지 않는다.

### P5 — 나머지 캔버스·문서 맥락 기능

1. 공통 캔버스의 관계·논리 그룹·텍스트·도형·다중 선택·실행 취소를 로컬 저장에 연결한다.
2. 파일 스냅샷·수동 버전 연결·현재 버전·복원·비교·후보 추천과 과거/기준일 검색을 구현한다.
3. 실제 파일 작업과 앱 내부 정리의 의미를 UI·단축키·오류 처리에서 일치시킨다.
4. 기능 목록의 남은 차이를 처리하고 웹·데스크톱 공통 시나리오로 회귀 검증한다.

완료 조건: 6절의 기능마다 구현·실제 검증·제약 상태와 근거가 기록되어 있다. 일부 기능의 미완료를 숨기지 않는다.

### P6 — 동기화 확장 기반 확인과 배포 검증

1. 장치 ID·문서/버전 ID·기준 revision·해시·변경 operation ID·삭제 표시의 계약을 정리한다.
2. 앱 metadata와 변경 기록의 원자성, 재시작 후 미처리 작업 복원을 검증한다.
3. 메타데이터의 기기별 경로와 비밀 키를 동기화 payload에서 제외한다. 대화·자료의 동기화 범위는 향후 별도 선택 대상으로 정의한다.
4. 자동 업로드나 네트워크 동기화는 켜지 않는다. 실제 sync transport와 충돌 병합 UI는 후속 구현 항목으로 명시한다.
5. 현재 OS의 앱을 패키징하고 그 실행 파일로 필수 사용자 시나리오를 다시 검사한다. Windows는 Windows에서 실행 검증하기 전까지 준비 상태로만 표시한다.

완료 조건: 로컬 앱의 핵심 흐름이 패키징된 앱에서도 동작하고, 동기화를 추가할 때 문서 모델·편집기를 다시 만들 필요가 없는 경계가 문서화되어 있다.

## 8. 밤샘 실행 운영 방식

- 최우선은 P0 → P1 → P2의 실제 사용자 흐름이다. 이후 P3 → P4 → P5 → P6 순서로 가능한 작업을 계속한다. 전체 목표의 미완료 항목은 유지한다.
- 시작 시점과 단계 완료 시점의 상태를 `docs/desktop-web-parity-progress.md`에 기록한다. 단계, 수정 범위, 검증 명령·결과, 제약, 다음 작업을 남기고 인증 정보·원문은 기록하지 않는다.
- DB·공통 화면·로컬 저장·AI처럼 서로 다른 경계는 작은 변경 단위로 진행한다. 기존 변경을 포함한 강제 reset·clean·일괄 덮어쓰기는 하지 않는다.
- 코드 안의 routine 구현 결정은 이 계획과 기존 지침으로 해결한다. 자격 증명·코드 서명·외부 서비스 설정이 부족하면 그 연동을 미검증으로 표시하고 로컬 구현과 독립적인 검증을 계속한다.
- 사용자 데이터·개발 DB·연결 폴더를 테스트 초기화 대상으로 쓰지 않는다. 실제 파괴적 파일 작업 검증은 전용 임시 폴더에서 수행한다.
- 무관한 의존성 업그레이드·프레임워크 교체·외부 배포·자동 동기화 활성화는 이번 실행에 섞지 않는다.
- 이 문서 작성 자체는 구현·예약 실행·백그라운드 실행을 시작한 것이 아니다. 실제 실행을 시작한 채팅이 위 단계와 진행 기록을 따라 작업한다.

## 9. 검증 계획

### 필수 시나리오

1. 웹 기존 작업 공간 접근·로그인·팀 권한, 데스크톱 기존 폴더·좌표·뷰포트의 회귀.
2. 양쪽에서 같은 문서 선택·패널 조작·편집·제안 적용·실행 취소 흐름.
3. 오프라인 로컬 편집·저장·재시작, 파일 이름 변경·교체 저장·원본 삭제·드라이브 해제·재연결.
4. 앱 두 창 또는 외부 앱의 동시 수정, 오래된 revision 거부, 저장 중 종료와 마이그레이션 복구.
5. 한글·공백 경로, 경로 이탈·심볼릭 링크·허용하지 않은 IPC 호출, 연결 폴더 외 접근 차단.
6. 현재·과거 문서 검색과 출처 버전 보존, 색인 변경·미완료·지원하지 않는 문서 상태.
7. 개인 키·기본 연결의 계정 분리, 만료·권한·크레딧 제한·네트워크·형식 오류, 키 삭제·교체·로그 미노출.
8. DOCX/HWPX 출력의 재파싱과 제목·본문·표·한글 대조, PDF 렌더링·TXT/MD 내용 확인.
9. 패키징된 앱에서 파서·파일 대화상자·키 저장·내보내기·재실행.

### 기존 검증 명령

`frontend`에서 타입 검사·린트·빌드를 실행한다. 변경 영향에 맞춰 문서·캔버스·편집·AI·버전·변환 시나리오를 선택하고, 최종 통합 단계에서는 영향받은 전체 묶음을 실행한다. 기존 Playwright 설정은 3100 포트를 공유하므로 서로 다른 설정의 명령은 순서대로 실행한다.

```bash
cd frontend
npm run typecheck
npm run lint
npm run build
npm run test:e2e
npm run test:documents
npm run test:canvas
npm run test:elements
npm run test:phase4
npm run test:versions
npm run test:intelligence
npm run test:rag
npm run test:writing
npm run test:conversion
```

데스크톱은 엔진·IPC·저장·마이그레이션 테스트를 실제 변경에 맞게 확장한다. 기존 `npm test`는 `engine.test.mjs`만 지정하므로 새 테스트 파일을 만들면 실행 스크립트에 포함한다. 새 E2E 파일도 현재 `testMatch`에 포함되도록 조정한다.

```bash
cd apps/desktop
npm run build
npm test
npm run test:e2e
npm run pack
```

패키징 앱 E2E는 현재 OS의 실제 실행 파일을 `CONTEXT_DESKTOP_EXECUTABLE`로 지정해 실행한다. 이후 runtime·자산·native 모듈을 다시 바꿨다면 패키징과 해당 검사를 반복한다.

백엔드 API·권한·AI provider를 변경하면 기존 전용 테스트 DB 컨테이너로 검증한다. Docker가 없으면 실행하지 못한 범위로 기록하고 가능한 순수 파서·응답 검증·단위 테스트를 수행한다.

```bash
docker compose --env-file .env.development -f docker-compose.yml -f docker-compose.test.yml --profile test run --build --rm backend-test
```

## 캔버스 상호작용 후속 구현 (2026-10-26)

두 손가락 이동·핀치 확대, 상태를 보존하는 우측 AI 패널 전환, 폴더별 지역 확대/클릭 탐색, 텍스트 겹침과 주변 항목의 가로 이동, 작은 빈 폴더와 테두리 호버를 웹·데스크톱에 공통 적용한다. 웹의 우측 AI 호출 버튼은 없애고 왼쪽 AI 메뉴를 사용한다. 중첩 폴더의 확대 한도는 폴더 및 내부 파일의 누적 축소율을 반영한다.

이웃 이동은 24 간격·160 이동 한도·8개 영향 한도와 같은 행 보존을 따르며, 초과 시 새 항목만 가까운 빈 곳을 찾는다. 논리 폴더 내부 항목이 경계를 벗어나지 않도록 검사하고 필요한 범위만 늘린다. 전체 자동 재배치와 메모에 따른 폴더 크기 변경은 하지 않는다. 추가 직전의 물리 폴더 자동 위치는 고정해 추가와 동시에 기존 영역이 재정렬되지 않게 한다.

추가 동작은 초기 로드·새로고침·외부 감시와 분리한다. 실제 새 텍스트 파일, 업로드·업로드 확인 복구, 복사본, 선택 요약을 같은 배치 저장 경로로 연결한다. 실패 시 배치 보상, 재요청 중복 방지, 파일을 삭제하지 않는 배치 undo/redo를 확인한다. 접근 가능한 이름·키보드 초점과 모션 감소 설정은 유지한다. 구현 결과와 실행 근거는 진행·검증 기록을 따른다.
